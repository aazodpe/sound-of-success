GradientBoosting

AdaBoost improved the ranking of songs without improving the ability to call one. Gradient boosting is the same idea built on a different engine: instead of arguing with the data about which rows deserve attention, it simply measures how wrong it currently is and fits the next tree to that.

Overview

Gradient boosting builds a running sum of small trees. It begins with a single flat guess — for a two-class problem, the overall rate at which songs chart — and then improves it one tree at a time. At every round it looks at how far the running total currently sits from the truth on each training row, fits a small tree to that, and adds the tree's output onto the total. The prediction after 200 rounds is not a vote among 200 models; it is one number that 200 models each pushed a little.

What each new tree is fitted to is the part worth being precise about. The quantity is the negative gradient of the loss with respect to the current prediction. That sounds abstract until the loss is named. If the loss is squared error, the negative gradient works out to be exactly y − prediction — the ordinary residual, the plain leftover. Each tree is literally fitted to the mistakes. For the two-class problem on this page the loss is log loss rather than squared error, so the leftover is y − p, the gap between what actually happened (1 or 0) and the probability the running total currently assigns. The principle does not change: every tree is trained on what is still wrong, which is why the target moves every round even though the data never does.

This is a genuinely different mechanism from the previous tab. AdaBoost keeps the target fixed and changes the data, raising the weight of rows it got wrong so the next stump is pulled toward them. Gradient boosting keeps the data fixed and changes the target, handing each new tree the current error as the thing to predict. AdaBoost then combines its members by a weighted vote; gradient boosting just adds its members up. The two are close cousins — AdaBoost turns out to be gradient boosting under one particular loss function — but in practice the additive form is more flexible, because any loss that can be differentiated can be boosted.

Two settings decide whether that flexibility helps or hurts. The learning rate scales every tree down before it is added, so a rate of 0.1 means each tree contributes a tenth of what it proposed. Shrinking the steps is not a slowdown for its own sake: a model that moves in small careful increments has many chances to correct its own direction, and reliably ends up in a better place than one that lunges. The price is that small steps need more of them. The number of trees is the other side of that trade, and it is the setting that can quietly ruin a boosted model. Because the running total is always being fitted to its own remaining error, and because some of that error is noise rather than signal, a long enough sequence will start modelling the accidents of the training set. Training error keeps falling the whole time — that is what makes it dangerous. The only way to see the problem is to score a separate validation set after every tree and watch for the point where it stops improving.

Data Prep

Gradient boosting is supervised, and it is fitted on exactly the partitions prepared for AdaBoost in Module 4, so that comparing the two at the end compares the methods rather than the data: 15,489 training songs, 5,164 validation and 5,164 test, verified disjoint, with the test set matching Module 3's row for row. The target is charted. The features are the ten numeric audio measurements plus the one-hot encoded genre, musical key and mode, 30 columns in total. The one-hot step is explained in full on the AdaBoost tab; the short version is that the three text columns are expanded into one indicator column per level so that no false ordering is invented between pop, rap and rock.

The three-way split is doing real work on this tab rather than ceremony. Everything below — learning rate, depth, and above all the number of trees — is chosen by scoring the validation rows. The test set was read once, after those choices were fixed.

Results

Three learning rates (0.03, 0.1, 0.3) were crossed with four tree depths (1, 2, 3, 5), giving twelve configurations, each fitted to 300 trees. For every one of them the validation score was recorded after each individual tree, so the number of trees is a third tuned setting rather than a constant: each configuration is credited with the best it ever reached, and with the round at which it reached it.

The chosen configuration was a learning rate of 0.1 at depth 3, stopped at 215 trees, with a validation AUC of 0.7620. The staged curve behind that choice is the clearest illustration of overfitting anywhere in this project.

The encoded categories earned their place here as well, for the second time in two modules. Fitting the chosen configuration on the ten numeric columns alone gives a validation AUC of 0.713; adding the twenty indicator columns raises it to 0.762. Knowing what kind of record something is keeps helping, no matter which method is asked.

Which did better? Gradient boosting, but only in the sense that matters least to anyone reading a prediction. It ranks songs better than AdaBoost by 0.0074 AUC and catches more than twice as many real hits, 29 against 14. It is also the first boosted model in the project to land below the do-nothing baseline on accuracy, by four hundredths of a percentage point. Both statements describe the same model, and the project's position after four modules is that the second one is the less informative of the two.

Conclusions

Gradient boosting is a better-built machine than AdaBoost and it produced a slightly better result, which is roughly what should have been expected. Fitting each tree to the current error, rather than arguing about which rows deserve more weight, is a more direct way of attacking the same problem, and it allows trees of depth three instead of depth one — enough to notice that two measurements together mean something that neither means alone. The reward for all of that was 0.0074 of ranking quality. The method worked, and the gain was small, and both of those facts belong in the same sentence.

The overfitting curve is the most instructive thing on this tab, and it is worth separating from the headline result. Training loss fell continuously for 300 trees while validation loss turned around after 157. Had the number of trees been fixed in advance at some plausible-sounding value, the model would have been quietly worse and nothing in the training output would have said so. The contrast between the chosen settings and the aggressive ones sharpens the point: an aggressive configuration peaked at 35 trees and lost 0.033 AUC by round 300, more than ten times what the careful configuration lost. The lesson is not that boosting overfits — everything overfits — but that the only reliable way to know when to stop is to hold data back and watch.

The deeper finding is one this tab shares with the three before it, and it has stopped being surprising. Another method, better machinery, more careful tuning, and the model still sits on the baseline and still cannot name a hit. It flagged 60 songs out of 5,164 and was right about 29 of them. That is not a failure of gradient boosting; it is a measurement of how much the audible properties of a recording have to say about its commercial fate, taken with a sharper instrument than before. The instrument keeps getting sharper and the answer keeps coming back the same.

One tab remains, and the honest expectation for it can be stated before the results arrive. XGBoost is a more refined implementation of exactly the mechanism described here, with an explicit penalty on complexity and a stopping rule that reads the validation set directly. It should edge ahead of gradient boosting on ranking by a small amount, and it should land in precisely the same place on accuracy. If that is what happens, the ceiling is not an artefact of any one method, and the project's central claim can be made with some confidence.
